# agent-dev-lab

このリポは AI エージェントで開発するとき、変更してから正しいと分かるまでの検証ループのどこで時間を待っているかを、台本で動く疑似の task の流れと合成の場面で再現して測る実験リポである。

## Why

AI エージェントに実装と検証を任せると、変更してから正しいと分かるまでの待ちが、作業時間の大半を占めるようになる。ある開発でこれを測ると、task 1本の時間の3分の2以上が検証の待ちだった。

待ちを決めていたのは1回の速さではなかった。エージェントは決められた手順どおりに、テスト用データの全件の投入のような重い工程を、1本の task の中で何度も流す（中央値で4回）。流す理由は、変更の確認、データどうしの ID の衝突の修正、確認者に渡す前にデータを元の状態へ戻すことのように、手順の作りから生まれていた。作業を何本も並べると、重い工程どうしが CPU を取り合い、1回の時間が倍近くに延びる。一方で、マシンを強くしても、データベースの書き込みを緩めても、待ちはほとんど縮まなかった。

ぶつかった壁そのものは、テスト用データの作り直しが遅い、共有するデータが干渉する、といったよく知られたものである。人のチームなら、データとテストが少しずつ増え、待ちが問題になるまでに長い時間がかかる。エージェントは人なら省く工程も毎回流し、同時に何本も走るので、同じ壁に数週間でぶつかる。

ただし、この観測はどれも1回ずつしか測っていない。このリポは同じ状況を合成のデータと台本で動く役で再現し、条件を固定して繰り返し測る。観測がばらつきの範囲内ではなかったか、対策がどの待ちを消したかを確かめる。

## Story

再現は架空のアプリを作る1つの開発として組む。物語は測る条件を並べるための設定である。場面の数のような物語の値は条件として決めたもので、結果の表の数字はすべてこのリポで測ったものである。

小さなチームがイベントの予約アプリを作る。進め方は [sdlc-kit](https://github.com/yktsnet/sdlc-kit) の `flow-team` の型に従う。相談者が Issue を起票し、実行者が Issue ごとに worktree を切って実装する。実行者は3本を並行させる（[dotfiles-public](https://github.com/yktsnet/dotfiles-public) の `i` と同じ回し方）。実行者のコミットは、別の文脈の確認者が Issue だけを基準に判定し、画面の操作役が画面をたどって確かめる。機能を1つ足すたびに、画面確認用のダミーデータ（場面）が1つ増え、どの実行者も変更のたびに全場面を投入し直す。

| 開発の時期 | 起きること | 測る問い |
|---|---|---|
| 1週目（場面40） | 全場面の投入は短く、誰も気にしない | 1 |
| 4週目（場面130） | 投入が延び、実行者を3本並べるとさらに延びる | 1・2 |
| 設定を疑う（4週目のころ） | マシンやデータベースの設定を疑って変えるが、縮まない | 3 |
| PR の記録を束ねる | sdlc-kit の `rework-review` で、PR 本文の `## 待ちと手戻り` を束ねる。1本の task で投入を何度も流す理由と、場面どうしの ID の衝突の繰り返しが分かる | 4・5 の動機 |
| 対策を入れる | dump から戻す、場面ごとに ID の範囲を割り当てる、画面の変更が止まってから操作役を流す | 4・5 |

問いと段取りは [PLAN.md](PLAN.md) にある。
